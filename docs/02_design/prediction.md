## 1. 積算温度（GDD）

- 入力: `weather_daily`（圃場ごと。3-1 で取り込み、1 日 1 行。気温は圃場の補正を加えた値。data-model.md）、基準温度 `base_temp_c`（品種、圃場×品種で上書き可。既定 14℃）
- 実装: `src/lib/gdd.ts`（3-2。純粋関数、`gdd.test.ts` で手計算と照合）
- 基準温度の解決: 圃場 × 品種の上書き（`field_cultivar_params.base_temp_c`）→ 品種の既定（`cultivars.base_temp_c`）→ 14℃。圃場の詳細の「予測の設定」で変える（5〜20℃）
- 日次 GDD = max(0, t_mean − base_temp)
  - `weather_hourly` があるときは、時間別に max(0, temp − base) を平均した値を使う（時間ごとに 0 で切ってから平均。冬の日較差が大きい日に精度が上がる）
  - **時間別を使うのは、その日（日本時間）の気温が 24 時間そろっている日だけ**。欠けた時間があれば日平均で計算する。日平均も時間別も無い日は「欠けた日」
  - どちらで計算したか（`hourly` / `daily`）を返す
  - 時間別は `weather_hourly_days`（0020 のビュー。日本時間の日ごとに気温の配列）で、必要な期間の分だけ読む（PostgREST の max_rows 1000 に当たらない）
- 期間の積算 = 開始日の翌日から終了日までの日次 GDD の合計（開始日当日は含めず、終了日は含める）。欠けた日は数えず（0 として足さず）、欠けた日数を返す
- 茎の画面（3-2）: 出蕾日の翌日〜昨日（今日の日次はまだ取り込まれていない）。収穫・終了した茎は収穫日・終了日まで。日数 N は今日（または収穫日・終了日）− 出蕾日。計算結果は保存しない（推定として保存するのは 3-3 から）
- 将来の積算は「平年値」を使う。平年値 = 過去データ（Open-Meteo の過去 API で取れる範囲、最低3年）の同じ日の平均。（当初はデータが足りない間は沖縄の月別平年気温をマスタとして持つ案だったが、3-3 で採らないことにした。2 章の「平年値が null の日」）
  - 決定（3-2）: 材料は 3-1 が保存する過去 10 年分の日次（`normalsRange`: 今年 1/1 の 10 年前〜昨年末）。同じ月日の日平均気温の平均
  - **2/29**: その年に 2/29 の値があればそれを、無ければその年の 2/28 と 3/1 の平均を 1 年分のサンプルにする（片方しか無い年はサンプルにしない）。2/28・3/1 の平年値には 2/29 を含めない
  - **サンプルが 3 年未満の月日は null**（予測での扱いは 2 章。7 日以内の欠けは前後から直線で補い、それより長い欠けに当たる予測は出さない）
  - 平年値の版 = 使った年の範囲（`normals-2016-2025` のような文字列）。3-3 の `estimates.inputs` に残す

## 2. 収穫予測日（`harvest_date`、MVP）

実装: `src/lib/prediction/harvest.ts`（純粋関数、`harvest.test.ts` で手計算と照合）、`src/lib/prediction/recompute.ts`（DB の読み書き。3-3）

- 対象: `status = flowered` の茎（lost・収穫済み・出蕾前は推定しない）
- 入力: 出蕾日（確認日 = `stems.bud_emerged_at`）、目標 GDD、基準温度、気温（実績と平年値）、被害（7 章）
  - 目標 GDD の解決: 圃場 × 品種の上書き（`field_cultivar_params.flowering_to_harvest_gdd`）→ 品種の既定（`cultivars.flowering_to_harvest_gdd`。暫定 900）→ 900。圃場の詳細の「予測の設定」で変える（100〜5,000）
  - 基準温度の解決は 1 章と同じ
- 計算: 出蕾日の翌日から 1 日ずつ GDD を足し、目標に達した最初の日 = 予測日
  1. 出蕾日の翌日〜**昨日**は実績（1 章の日次 GDD。時間別が 24 時間そろった日は時間別）。今日の日次はまだ取り込まれていないので実績は昨日まで
  2. **今日**から先は平年値: max(0, 平年の日平均 − 基準温度)。（タスクの記述の「明日以降」は「実績の翌日以降」と読み、今日も平年値で数える。今日を飛ばすと 1 日分の GDD が抜けて予測が早まる）
  3. 実績の期間で気温の欠けた日は、その日の平年値で補う（0 として足すと予測が遅れる方向に偏るため）。補った日数は `inputs.actual_missing_days`
  4. 実績だけで目標を超えていれば、予測日は実績で達した日（過去の日）になる
  5. 出蕾から 730 日で達しない（平年値がずっと基準温度以下など）なら予測しない（理由 `never_reaches`）
- 幅: 目標 GDD の ±10%。0.9 倍に達する日 = `lower_date`、1.1 倍に達する日 = `upper_date`（実績が溜まったら、圃場×季節の実績の分散から決める）
- **平年値が null の日（サンプル 3 年未満、1 章）の扱い（3-3 で決定）**
  - 前後の値のある月日から直線で補う（年をまたいで円環で探す）。ただし **null が 7 日を超えて続く区間は補わない**
  - 予測に使う日（今日〜1.1 倍に達する日、と実績の欠けた日）に補えない日があれば予測しない（`unavailable`、理由 `normals_gap`、最初の日を `inputs.unavailable_date`）。平年値の材料がまったく無ければ理由 `no_normals`
  - 補った日数は `inputs.normals_filled_days`
  - 根拠: 平年値は季節の滑らかな曲線で、沖縄の日平均の季節変化は 1 週間で 1℃ 未満。7 日以内の欠けを直線で補った誤差は 1 日あたり GDD で 0.5 前後で、目標の ±10%（約 ±90 ℃・日）の幅に比べて無視できる。7 日を超えて欠けるのは、10 年分の材料の取り込みが途中（3-1 は 1 回の実行時間で打ち切り、次回に続きから取る）か障害で年単位に抜けているときで、補うと誤った予測を出すおそれがある。そのときは予測を出さず理由を見せ、材料がそろった後の日次の取り込みで再計算されるのを待つ。月別平年気温のマスタで補う案は、材料が取れる限り不要なので採らない
- 出蕾日に幅（`earliest_at`）があっても確認日を使い、`inputs.earliest_at` に残すだけ。出蕾時の累計葉数（出蕾イベントの payload のスナップショット）は予測に使わない（4 章の「どちらを使うか」は、予測には関係しないことで決着）

### 保存（estimates に追記）
- `estimates`（`kind = harvest_date`）に追記する。**上書き・削除しない**（0021 で estimates の RLS を select / insert だけにした）。最新は `computed_at desc` の先頭（ビュー `latest_estimates`、0021）
- `model_version` = `harvest-gdd-v1`
- `inputs`: `bud_date`（確認日）、`earliest_at`、`target_gdd` と `target_gdd_source`（field / cultivar / default）、`base_temp_c` と `base_temp_source`、`range_ratio`（0.1）、`actual_from` / `actual_to`（実績の期間）、`actual_gdd`（実績の積算、小数 2 桁）、`actual_days`、`actual_missing_days`、`normals_version`（`normals-2016-2025` のような平年値の版）、`normals_filled_days`、`damage`（`severe` / null）と `damage_events`（要確認の根拠の被害イベント）
- 予測できなかったとき（`normals_gap` / `no_normals` / `never_reaches`）も、日付を null にした行を追記し、`inputs.unavailable_reason`（と `unavailable_date`）に理由を残す（画面が理由を出せるように。予測一覧 3-6 は value_date が null の行を数えない）
- **前回の推定（latest_estimates）と日付・版・入力がすべて同じなら追記しない**（再計算の入口が重なっても行を増やさない）。入力が 1 つでも変われば（実績が 1 日増えた・目標を変えた・被害が付いた）追記する

### 再計算のタイミング
- 出蕾・茎の被害の記録: 端末の outbox から同期ワーカーが RPC で送った直後に、同期ワーカー（`src/lib/offline/sender.ts`）が Route Handler `POST /api/predictions/recompute`（ログイン中のユーザーの権限、RLS で自組織の茎だけ）を呼ぶ。失敗してもイベントの送信は成功のまま（推定は下の入口で追いつく）。呼び終えてから同期の完了を知らせるので、同期の後の再描画で予測が出る
- 出蕾日・被害の訂正（2-6、Server Action）の後
- 圃場・株の severe の被害（2-5、Server Action）の後: その圃場・株の出蕾済みの茎
- 予測の設定（目標 GDD・基準温度）の保存の後: その圃場のその品種の出蕾済みの茎
- 日次の気温取り込み（3-1 の Cron。service_role）の後と、圃場の詳細の「今すぐ取り込む」の後: その圃場の出蕾済みの茎。取り込みに失敗しても、あるだけの気温で再計算する
- 茎の画面を開いたとき、出蕾済みなのに推定が 1 件も無ければ 1 回計算して追記する（再計算の呼び出しが届かなかったときの取りこぼし対策。推定がある茎は画面を開いても書かない）

### 表示
- 茎の画面（3-3）: 「収穫予測: ◯月◯日ごろ（◯日〜◯日）」（幅が月をまたぐときは「10月28日〜11月8日」）。要確認なら「要確認」の印と「大きな被害（程度: 重）の記録があります」。予測できなければ理由。補助の文字で計算した日。出蕾済み（見かけの状態が flowered）のときだけ。オフラインの殻では推定をキャッシュしないので理由だけ
- 株の詳細の茎一覧: 出蕾済みの茎に「収穫予測 ◯月◯日ごろ」と要確認の印

### 補正
収穫実績が溜まったら、圃場×品種ごとに「出蕾→収穫の実績 GDD」の中央値を `field_cultivar_params.flowering_to_harvest_gdd` として提案する（自動で書き換えず、設定画面で採用する）。

## 3. 果房重量（`bunch_weight_kg`、MVP。実績が溜まってから有効化）

- 対象: `flowered` の茎（出蕾時の記録があるもの）
- 入力: 出蕾時の偽茎周囲長、生葉数、段数、出蕾月
- モデル: 最初は線形回帰（周囲長、生葉数、段数、季節ダミー）。実績 20 房未満なら計算しない（「未算出」）
- 幅: 回帰の残差の標準偏差で lower / upper
- 学習データ: `harvested` イベントの `weight_kg` と、その茎の出蕾時の記録。組織内のデータだけを使う（将来、品種が同じなら組織横断も検討）
- `model_version` に「linear-v1 / 学習に使った房数 / 学習日」を入れる

## 4. 累計葉数の推定（`cumulative_leaves`、補助）

- 訪問できなかった期間（前回の `leaves_new` から 21 日以上）がある茎に対して、「GDD あたりの出葉速度」から推定値を出す
- 出葉速度 = その圃場の実績（leaves_new の合計 ÷ 同期間の GDD）。実績がない間は文献値（暖期で 7〜10 日に1枚相当）
- 推定値は観測と併存させ、画面では「推定」と明示する。累計葉数の正式な値は観測のみから計算する
- 出蕾イベントの payload の `cumulative_leaves` は出蕾時点の記録（スナップショット）で、出蕾より前の `leaves_new` を訂正（2-6）しても自動では直さない。食い違うと茎の画面に「出蕾時の累計葉数（記録）/ 現在の計算」の両方が出る。決定（3-3）: 収穫予測日はどちらも使わない（出蕾日と積算温度だけで決める）。果房重量（3 章）でどちらを使うかはステップ 4 で決める

## 5. 出蕾予測（`bud_date`、MVP 外）

- 累計葉数と `leaves_to_flowering` の差 ÷ 出葉速度 → 日数 → 平年値で日付化
- `leaves_to_flowering` は1作目の出蕾実績から圃場×品種で決める。それまでは計算しない

## 6. 提案ルール

実行タイミング: イベント記録時、および日次バッチ。同じ対象・同じ kind で `open` があれば作らない。

| kind | 条件 | due_at | reason |
|---|---|---|---|
| `bag` | `bud_emerged` から N 日経過（N は設定。初期値は要確認）で `bagged` がない | 出蕾日 + N | 「出蕾から N 日」 |
| `debud` | 同上（袋掛けと同時に提案） | 同上 | |
| `harvest_window` | `harvest_date` の lower が 7 日以内 | lower | 「積算温度が目安に到達」 |
| `fertilize_after_harvest` | `harvested` が記録され、その株に M 日以内の `fertilized` がない | 収穫日 + M | 「収穫後の追肥」。量は圃場標準＋株差分 |
| `remove_dead_leaves` | 最後の `leaves_removed` から X 日以上、かつ茎が active / flowered | 今日 | |
| `inspect` | 累計葉数の検算ずれ ≥ 3、または `damage` の severity が severe / lost | 今日 | ずれの枚数、被害の内容 |

- 対象が `lost` / `harvested` / `removed` / `transplanted` になった茎の `open` な提案は自動で `dismissed` にする（reason に「対象が終了」）
- 「実施した」= `done`、「無視」= `dismissed`。どちらも `resolved_at` / `resolved_by` を残す

## 7. 被害による予測の見直し

決定（3-3）:
- `damage` の severity が `lost` → 茎を `lost` にし（0009）、推定を出さない（再計算の対象外。それまでの推定は消さずに残るが、画面には出さない）。週次の出荷見込みから外す
- 茎の `severe` → 推定は出すが「要確認」（`inputs.damage = severe`、根拠の被害イベントを `inputs.damage_events`）。週次見込みでは「不確実」として別枠で数える
- **圃場・株の `severe` の被害（target_type = field / mat、2-5）も、その圃場・株の出蕾済みの茎を「要確認」にする**。ただし**茎の開始日（`started_at`）より前に起きた**圃場・株の被害は、その茎に関係しないので数えない（数えると、古い台風の記録で以後のすべての茎が要確認になり続ける）
- `moderate` / `light` → 変更なし（将来、実績から重量への影響を推定する）
- 訂正済み（`superseded_by` あり）の被害は数えない。被害の程度を訂正すると再計算する

## 8. 週ごとの出荷見込み

- 対象: `flowered` の茎で `harvest_date` の最新推定があるもの（`lost` を除く）
- 週 = 月曜始まり。予測日の value_date が入る週に本数を数える
- 見込み kg = その週の茎の `bunch_weight_kg` の合計（未算出の茎は本数のみ）
- 「不確実」= severe の被害がある茎、または lower〜upper が 3 週以上にまたがる茎。別枠で表示
- 将来の販売アプリは、この集計を API で返す
