# 速度の計測（PERF-1）

本番（https://banana-manufacturer-8f7t.vercel.app）で、画面表示と +1 の記録の往復を「計測 → 直す → 同じ条件で計測」する。

## 計測の方法

スクリプト: `scripts/perf/measure.mjs`（Playwright を Node から直接使う。結果の JSON は `scripts/perf/results/`）

```bash
node scripts/perf/measure.mjs before
```

- アカウント: テスト農園 A（`.env.local` の `E2E_EMAIL` / `E2E_PASSWORD`）。ブラウザからのログインは 1 回の計測で 1 回だけ（Supabase Auth のレート制限）
- データ: スクリプトの冒頭で、ログインしたブラウザの Cookie から取り出したセッションで `supabase-js` から圃場（名前は `E2E計測-…`。E2E の setup の掃除で消える）・株 1・茎 1・葉の観測 6 件を作る。本番組織のデータには触れない
- ブラウザ: Chromium、iPhone 相当の幅（390×844、モバイル・タッチ）、Service Worker は有効（実際の PWA と同じ）
- 計測する場所: 開発者の PC（日本。Vercel のエッジは `kix1`（大阪）に着く。この PC から Supabase への往復は暖まった接続で約 60 ms）
- 各項目 **5 回**、値は **中央値**
  - **画面表示**: `page.goto`（ページ全体の読み込み）で開き、ナビゲーション開始から主要な要素が表示されるまで（`performance.now()`）
    - ホーム: 圃場の行 / 圃場一覧: 圃場の行 / 圃場詳細: 圃場名 / 株の詳細: 茎の行 / 茎の画面: +1 ボタン
  - **TTFB**: `performance.getEntriesByType('navigation')[0].responseStart`
  - **株→茎（タップ）**: 株の詳細で茎の行をタップしてから（クライアント遷移）、茎の画面の +1 ボタンが表示されるまで。PWA での普段の操作
  - **+1 の記録**: 茎の画面で +1 を押してから
    - **未同期 0**: ヘッダの未同期件数が 1 → 0 に戻るまで（ブラウザ → Supabase の直接の書き込み）
    - **refresh 応答**: 同期の後の `router.refresh()`（この茎の画面の RSC、`?_rsc=`）の応答が終わるまで（Resource Timing の `responseEnd`）。サーバーの最新が画面に揃うまで ＝ **記録の往復**

### 分かったこと

1. **遅いのはサーバー（Vercel の関数）の中**。どの画面も表示の 8〜9 割が TTFB（サーバーが返し始めるまで）。ブラウザの描画・JS は数百 ms
2. **+1 の書き込み自体は速い**（約 130 ms。ブラウザから東京の Supabase に直接書く）。遅いのはその後の `router.refresh()` で、茎の画面をサーバーで描き直すのに 1.7 s
3. 画面のサーバー処理は Supabase への往復が直列に 3〜5 回（proxy の `getUser`、画面の `getUser`、親の select → 子の select …）。1 往復が数百 ms かかるので、回数がそのまま時間になる
4. ホームの文書は `x-vercel-cache: HIT`（静的シェルはキャッシュ）でも TTFB が 1.3 s。proxy（`getUser` のネットワーク往復）がキャッシュの前に毎回走るため

### 打ち手（数字から）

| 打ち手 | 効く理由 | 見込み |
|---|---|---|
| Vercel の関数を東京（`hnd1`）に置く（`vercel.json`） | 1 往復 数百 ms → 数 ms。直列の回数 × 往復時間の「往復時間」を消す | 最大。各画面・refresh が 1 s 以上短くなるはず |
| proxy を `getClaims()`（ES256 の JWT をローカルで署名検証）に | proxy の 1 往復を毎リクエスト消す。この Supabase は非対称鍵（ES256、JWKS あり）なので `getClaims` はネットワークに出ない（JWKS はインスタンスごとにキャッシュ） | 1 往復分 |
| 画面の直列の select を並列 / 1 回にまとめる（茎・株の画面） | 直列の回数を減らす | 1〜2 往復分 |

## 後（2026-10-25、5840c35 のデプロイ後）

結果: `scripts/perf/results/after-20261025035027.json`。前と同じスクリプト・同じ PC・同じ条件（各 5 回、中央値）。ただし「前」の計測の後に、応答ヘッダ `server-timing` を記録する 1 行だけ足した（時間の測り方は同じ）。
新しいデプロイであることは、proxy が付ける `Server-Timing` ヘッダ（5840c35 で追加）が本番の応答に出ていることで確かめた。

### 変えたこと

1. `vercel.json` に `"regions": ["hnd1"]`（関数を東京に）
2. proxy の認証を `getUser()`（Auth サーバーへの往復）から `getClaims()`（ES256 の JWT をローカルで署名・期限検証。JWKS はインスタンスで 10 分キャッシュ）に
3. Server Component / Action の `getUser()` を 1 リクエスト 1 回に（`src/lib/auth/current-user.ts` の `cache()` で包んだ `getCurrentUser`）。サーバー用 Supabase クライアントも 1 リクエスト 1 つ
4. 直列の select を並列（`Promise.all`）か 1 回の select（リレーションの埋め込み）にまとめた。proxy を含む Supabase への直列の往復: 茎の画面 4 → 1、株の詳細 5 → 1、圃場一覧・圃場詳細 3 → 1、ホーム 3 → 2、茎の登録 5 → 2 など

### 分かったこと・残ったこと

- **効いたもの**: リージョン（往復時間）と往復回数の削減の掛け算。前は「直列 3〜5 回 × 1 回 300 ms 前後」だったのが、後は TTFB 250〜350 ms で、その大半はこの PC → Vercel のエッジ → 関数の経路（静的なログイン画面でも curl で約 0.2 s）
- **proxy の認証**: `Server-Timing: auth;dur=1〜4ms` で、proxy の認証確認はネットワークに出ていない（`getClaims` のローカル検証）
- **proxy の実行場所が sin1（シンガポール）**: `Server-Timing` の desc（`process.env.VERCEL_REGION`）は `sin1` だった。`vercel.json` の `regions` が proxy には効いていない可能性がある。proxy は Supabase に往復しなくなったので Supabase との距離は効かないが、エッジ（kix1）→ sin1 → 画面の関数、という経路の分だけ遅れている可能性がある。画面の関数（Server Component）のリージョンはヘッダに出しておらず、確認していない（後のサーバー内の時間が短いことから東京か近いと推定）。**Vercel ダッシュボードの Functions 欄で proxy と画面の関数のリージョンを確認するのはステップ 2 に持ち越す**
- ホーム・圃場一覧は表示が TTFB より 300〜400 ms 長い（他の画面は 30〜40 ms）。クライアント側（「最近開いた株」など端末の IndexedDB を読む部品、JS の読み込み）の分と思われる。今回は手を入れていない
- ステップ 2 に持ち越し: 読み取りのローカルキャッシュ（Dexie）と差分同期で、画面遷移をサーバー往復なしで出す（offline-sync.md 5 章）。+1 の後の `router.refresh()` を茎の画面だけの再取得にする
- reviewer（PASS）の軽微な指摘で、ステップ 2 に持ち越すもの:
  - proxy の `getClaims()` が throw する経路（JWKS にある kid で未対応の alg を持つ偽の Cookie）を try/catch して「未ログイン」として扱う（今は 500。アクセスは許さないので安全側だが、/login に転送すべき）
  - `Server-Timing`（リージョンと認証の所要時間）は、リージョンの確認が済んだら外すか計測時だけにする
  - 株の詳細の mat の select の `error` を確かめる（埋め込みの関係が壊れると今は 404 に見える。茎の画面と同じく throw に）
