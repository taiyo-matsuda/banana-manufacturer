# 要件定義

最終更新: 2026-10-21
この文書は「何を作るか」だけを書く。技術的な実現方法は `02_design/` に書く。

---

## 1. 目的

バナナ（ドワーフナムワ、沖縄・露地）の圃場・株・茎ごとの栽培上の事実を継続的に蓄積し、
そのデータから「いつ・何kg収穫できるか」を把握・予測できるようにする。

### 方針
- **作業管理より事実の蓄積を優先する。** 巡回支援は「データを集めるため」の位置づけ。
- **観測（事実）・推定・提案の3層を分ける。** 観測は追記のみ。推定は後から再計算できる。提案は採用・無視の記録を残す。
- **最初は一人で使うが、複数農家・複数ユーザーに広げられる構造にしておく。**
- **予測はルール＋統計から始め、自圃場の実績で補正する。** 機械学習は実績が溜まってから。
- **予測と実績のずれ自体を改善用のデータとして残す。**

### 将来の展開（今は作らないが、構造で阻害しない）
- 作業スタッフによる記録（誰が記録したかを残す）
- 他農家への提供（農家ごとのデータ分離、招待制）
- 販売アプリ（週ごとの出荷見込みの公開、予約、トレーサビリティ）
- ドローン（Mavic 3 Enterprise / Multispectral）による株単位の定期撮影と樹勢マップ

## 3. 栽培の前提（ドメイン知識）

| 項目 | 内容 |
|---|---|
| 品種 | ドワーフナムワ（ABB、矮性）。文献値が乏しいため自圃場実績で補正する前提。品種は株ごとに持ち、1圃場に複数品種があってよい |
| 栽培 | 沖縄、露地。圃場2つ、合計25a、今後拡大。株間3m。畝の概念は使わない |
| 苗 | 吸芽苗または組織培養苗。これから植え付け。既存記録なし |
| 仕立て | 3本仕立て。親・子・孫と時期をずらして残す。株ごとに栽培中の茎は最大3本 |
| 吸芽の扱い | 3本を超える吸芽は、芽かきするか、掘り上げて別の位置（同じ圃場または別の圃場）に植え替えて新しい株とする。新しい株は由来（元の株・茎）を記録する |
| 土壌分析 | 圃場単位。採取地点は記録しない（農家ごとに採取方法が異なるため） |
| 施肥 | 株単位で記録する。入力は圃場一括＋例外の株だけ修正 |
| 収穫 | 果房の重量のみ記録。等級は記録しない |
| 無農薬 | 塗料などの印は使わない。葉の印は園芸用クリップ（洗濯ばさみ型） |
| 気象の影響 | 冬（平均15〜18℃）は生育がほぼ停滞。台風（7〜10月）の被害が予測を外す主因 |

### バナナの生育と予測に関する前提
- 葉は茎の中心から1枚ずつ順に出る。暖期で7〜10日に1枚、冬は大幅に遅くなる。
- 出蕾は、茎が生涯に出した葉の累計枚数にほぼ依存する（品種ごとに概ね一定）。
- 出蕾から収穫までは積算温度で見込める（基準温度14℃前後、文献目安900℃日前後。要補正）。沖縄では季節により3〜5か月。
- 果房の重さは、出蕾時の偽茎周囲長・生葉数・段数・季節で概ね説明できる。

## 4. 記録する事実

### 4.1 単位
```
組織（農家）
 └ 圃場            … 名前、代表点、土壌分析
    └ 株           … 圃場内の固定位置、品種、植え付け日、由来
       └ 茎        … 親→子→孫。状態、苗種、初期葉数
          ├ 観測   … 葉数など、時点の値
          ├ イベント … 出蕾、袋掛け、収穫、被害、枯葉除去、施肥、吸芽の採用・除去・株分け
          └ 写真
```

### 4.2 観測（時点の値）

| 観測 | 内容 | 頻度 |
|---|---|---|
| 新たに開いた葉の枚数（`leaves_new`） | 前回の印から新たに開いた葉の枚数。通常 0〜2 | 1〜2週に1回（夏は週1、冬は月1）。各株で最も進んだ茎を優先、子・孫は月1 |
| 現在の葉の枚数（`leaves_current`） | 今ついている葉の枚数 | 月1回、出蕾時、収穫時 |
| 偽茎周囲長 | 地上1mの周囲長（cm） | 出蕾時 |
| 高さ | 任意 | 任意 |

### 4.3 イベント（起きた事実）

| イベント | 対象 | 記録する内容 |
|---|---|---|
| 出蕾 | 茎 | 確認日、前回訪問日（幅を持たせる）、その時点の累計葉数（自動）、生葉数、偽茎周囲長 |
| 段数の確定 | 茎 | 段数（苞が開ききった時点） |
| 袋掛け | 茎 | 日付 |
| 摘蕾 | 茎 | 日付 |
| 収穫 | 茎 | 日付、果房重量（kg、小数1桁） |
| 枯葉除去 | 茎 | 日付、除去枚数 |
| 施肥 | 株 | 日付、肥料名、量、単位 |
| 被害 | 圃場 / 株 / 茎 | 日付、種類（倒伏・裂葉・折損・寒害・病害）、程度（軽・中・重・喪失） |
| 吸芽の発生・採用・除去・株分け | 茎 | 日付、株分けなら転出先の株 |
| 茎の終了、株の撤去 | 茎 / 株 | 日付 |

### 4.4 写真
- 茎・株・圃場のいずれかを対象に撮る。観測やイベントに添えてもよいし、巡回で撮っただけでもよい。
- 撮影日時、撮影位置、種類（横から・蕾・果房・被害・その他）を残す。
- MVP では写真を解析しない。記録と検証、将来の学習データのために溜める。

### 4.5 外部データ
- 気温（時間別）、降水量、最大風速を圃場ごとに自動で取得し、積算温度を計算する。
- 土壌分析の結果は手入力する（項目は分析機関に合わせる。要確認）。

## 5. 記録の定義（他農家と比較可能にするための統一ルール）

### 5.1 葉数
- **1枚と数える基準**: 葉が完全に開いた時点。巻いている新葉（シガーリーフ）は数えない。
- **累計葉数**（出蕾予測用）= 初期葉数 + Σ 新たに開いた葉の枚数
- **検算**: 累計 ≒ 現在の葉の枚数（最新）+ 除去した葉の合計。差が3枚以上なら「確認」を促す。
- **印の方法**: 最新の展開葉の葉柄に園芸用クリップを挟む。訪問ごとに色を替える（2〜3色を循環）。訪問時はクリップより上に開いた葉を数え、クリップを付け替える。
- **印が外れていた場合**: その回は未記録とし、積算温度からの推定で穴埋めする（推定であることを明示）。
- **剣葉**（吸芽の初期の細い葉）: 累計に含める。「幅広の葉が出始めた日」を別に記録し、後から数え方を切り替えられるようにする。
- **数え始め**: 組織培養苗は植え付け時の葉数、吸芽は株として採用した時点の葉数を初期値とする。

### 5.2 出蕾
- 出蕾日は「蕾が確認できた日」。訪問間隔があるため「前回訪問日〜確認日」の幅を持つ。
- 出蕾時に累計葉数（自動）、生葉数、偽茎周囲長を記録する。段数は苞が開ききった時点で別に記録する。

### 5.3 被害
- 程度が「喪失」の茎は予測から除外する。「重」は要確認として扱う。

### 5.4 訂正
- 観測・イベントは削除しない。間違えた場合は訂正レコードを追加し、元のレコードは「訂正済み」として残す。
- 画面では最新の値だけを見せ、履歴から元の値をたどれる。

## 6. ユースケース（MVP）

### UC-1 圃場と株を登録する（植え付け時）
1. 圃場を登録する（名前、地図上の代表点）
2. 航空写真を見ながら株を配置する。株間 3m の格子を「列数 × 本数」で自動生成し、ずれた株はドラッグで直す
3. 株ごとに品種（既定: ドワーフナムワ）、植え付け日、苗の種類、初期葉数を登録する（一括で同じ値を入れ、例外だけ直す）

### UC-2 巡回して記録する（1株あたり 20〜30 秒）
1. 地図、または現在地に近い株の候補から株を選ぶ
2. 最も進んだ茎を開く
3. 「+0 / +1 / +2」で新たに開いた葉を記録する
4. クリップを付け替える
5. 横から写真を1枚撮る
6. 必要ならイベント（出蕾など）を記録する
7. 圏外でも保存され、通信が戻ったら自動で同期される

### UC-3 出蕾・袋掛け・収穫を記録する
- 出蕾を記録すると、その茎の収穫予測日が表示される
- 袋掛け・摘蕾の時期になると提案が表示される
- 収穫を記録すると重量が出荷実績として積み上がる

### UC-4 吸芽を管理する
- 吸芽の発生を記録し、残す（採用）・芽かき・株分けのいずれかを選ぶ
- 採用すると株の茎として追加される（栽培中は最大3本）
- 株分けすると、植え替え先の位置に新しい株が作られ、由来が記録される

### UC-5 施肥を記録する
- 圃場全体に同じ施肥を一括登録し、例外の株だけ修正する

### UC-6 被害を記録する（台風後など）
- 圃場・株・茎のいずれかを対象に、種類と程度を記録する
- 「喪失」の茎は予測から外れる

### UC-7 予測と出荷見込みを見る（PC）
- 茎ごとの収穫予測日と推定重量
- 週ごとの収穫予定本数と見込み kg

### UC-8 土壌分析を記録する
- 圃場ごとに分析日と項目値を入力する

## 7. 予測と提案（MVP）

| 予測 | MVP | 根拠となる記録 |
|---|---|---|
| 収穫時期 | 入れる | 出蕾日 + 積算温度（品種の目安を自圃場実績で補正） |
| 果房の重さ | 入れる（収穫実績が 20〜30 房たまってから有効化。それまでは「未算出」） | 出蕾時の偽茎周囲長・生葉数・段数・出蕾月 と 収穫重量の実績 |
| 出蕾時期 | 入れない（データは取る） | 累計葉数、気温 |
| 累計葉数の推定 | 補助 | 訪問できなかった期間を積算温度から推定する |

| 提案 | きっかけ |
|---|---|
| 袋掛け・摘蕾 | 出蕾から N 日後（N は要確認） |
| 収穫期 | 出蕾からの積算温度が目安に近づいたとき（幅で表示） |
| 収穫後の追肥 | 収穫を記録したとき。量は圃場標準＋株ごとの差分 |
| 枯葉処理 | 前回の枯葉処理から X 日（X は要確認）。写真からの判定は将来 |
| 確認 | 累計葉数の検算がずれたとき、被害が「重」「喪失」のとき |

提案は「実施した」「無視した」を記録し、将来の精度改善に使う。

## 8. MVP の範囲

### 入れる
- 圃場・株・茎の登録、地図での株の配置
- 観測・イベント・写真の記録（iPhone、オフライン対応）
- 気象の自動取得と積算温度
- 収穫予測日、果房重量の推定（実績が溜まり次第）
- 提案（袋掛け・摘蕾、収穫期、収穫後の追肥、枯葉処理、確認）
- 週ごとの出荷見込み（PC）
- 土壌分析の入力

### 入れない
- 出蕾予測
- 写真の画像解析（枯葉判定など）
- ドローン画像の取り込み
- スタッフの権限管理、招待、課金
- 販売アプリ
- 通知（アプリを開いたときに提案が見えれば足りる）

## 9. 非機能要件

| 項目 | 要件 |
|---|---|
| 端末 | iPhone（Safari）。PC のブラウザでも同じ画面を使う。ホーム画面に追加して使う |
| オフライン | 圏外で記録（写真含む）でき、通信が戻ったら自動で同期する。未同期件数を常に表示する |
| 利用者の制限 | 自分で登録（Sign Up）できない。アカウントは管理者が作る。サイト全体を許可された人だけが開ける |
| データの分離 | 農家（組織）ごとにデータが分かれ、他の農家のデータは見えない |
| 追記のみ | 観測・イベントは削除しない。訂正は訂正レコードで行う |
| 推定の再計算 | 予測の計算方法を変えたとき、過去の推定を残したまま再計算できる |
| データの持ち出し | 自分のデータを CSV 等で取り出せる（要確認。MVP に入れるか） |
