1タスク = implementer が1回で実装し、reviewer が1回で判定できる大きさ。

PASS になったタスクだけ `[x]` にする。FAIL は指摘を添えて implementer に差し戻す。

## ステップ 2: 巡回を支える

目的: 植え付け後の毎週の巡回を速く・漏れなくする。1 タスクずつゲートを通す。依存の順に並べてある（2-1 → 2-2 は必須の順序、ほかは独立）。
累計葉数の検算（CLAUDE.md のステップ 2 の項目）は 1-6 で実装済み（ずれ 3 枚以上で警告）。

- [x] **2-1 吸芽の発生の記録**（要件 5.3、data-model の `sucker_emerged`）
  - 株の詳細に「吸芽が出た」。入力: 方向（8 方位のボタン）、種類（剣葉 / 水吸芽）、確認日（既定 今日）。親茎は株の栽培中の茎のうち最も世代の若い茎（選び直せる）
  - 新しいマイグレーションの RPC（`record_stem_event` と同じく security invoker、`p_id` で冪等）で、`stems` に `status=sucker`、`parent_stem_id`、`generation=親+1`、`started_at` の行を作り、親茎に `sucker_emerged` イベント（payload: `sucker_stem_id`, `parent_cumulative_leaves`（その時点の親の累計葉数。端末で計算）, `earliest_at`, `direction`, `sucker_type`）を同じトランザクションで記録する
  - オフラインでも記録できる（1-9 の outbox 経由。茎の id は端末で採番）
  - 吸芽（`sucker`）は最大 3 本の制約に数えない（0001 のトリガーは active / flowered だけを数える）
  - 完了条件:
    1. 吸芽を記録すると株の詳細に「吸芽」として表示され、親茎のイベント履歴に方向・種類・**その時点の親の累計葉数**が出る
    2. オフラインで記録し、オンラインに戻すと stems と events の両方がサーバーにある。再送しても二重にならない
    3. 栽培中の茎が 3 本の株でも吸芽は記録できる

- [x] **2-2 吸芽の採用・芽かき・株分け**（要件 3 章「吸芽の扱い」、UC-4）
  - 吸芽の茎に「採用」「芽かき」「株分け」
  - 採用: 初期葉数を入力 → `status=active`、`adopted_at`、`initial_leaf_count`。栽培中が 3 本なら採用できず理由を表示（DB トリガーが正本）
  - 芽かき: 確認ダイアログ → `status=removed`、`ended_at`
  - 株分け: 転出先の圃場を選び、地図の空いている位置をタップ → 新しい株（`origin_type=sucker_transplant`、`origin_stem_id`=この吸芽、品種は元の株と同じ、植え付け日=今日）と、その generation 1 の茎（`started_at` は吸芽の `started_at` を引き継ぐ、初期葉数を入力）を作り、吸芽は `status=transplanted`。新しい株の詳細に「由来: 元の株コード」のリンク
  - 3 つとも RPC で 1 トランザクション（イベント `sucker_adopted` / `sucker_removed` / `sucker_transplanted` を記録）。採用と芽かきはオフライン可、株分けは株の作成を伴うのでオンラインのみ（設計どおり）
  - 完了条件:
    1. 採用すると栽培中の茎として一覧に出て、累計葉数 = 初期葉数。3 本目の後の採用は拒否される
    2. 芽かきした吸芽は「芽かき」として表示され、記録ボタンが出ない
    3. 株分けすると転出先に新しい株ができ、由来をたどれる。元の吸芽は「株分け」状態になる

- [x] **2-3 株の位置の修正と撤去**（要確認 11）
  - 地図の「位置を直す」モードで既存の株をドラッグ → 確定で `mats.lat/lng` を更新
  - 株の撤去: 株の詳細の編集画面から「撤去」（確認ダイアログ）→ `mats.status=removed` ＋ `mat_removed` イベント。栽培中の茎があれば撤去できず理由を表示
  - 撤去した株は地図・圃場の株一覧に出さない（株の詳細の URL は開ける。「撤去済み」と表示）
  - 完了条件:
    1. 株を 1 つドラッグして確定すると、再読み込み後も新しい位置にある。他の株は動かない
    2. 撤去した株は地図から消え、株の詳細は「撤去済み」。栽培中の茎がある株は撤去できない

- [x] **2-4 施肥の一括入力**（要件 4.4、画面 5）
  - `/fields/[fieldId]/fertilize`: 日付、肥料名（前回の入力を候補に）、量、単位（kg / g / L / mL）→ 対象の株の一覧（既定は圃場の撤去していない全株）で、例外の株は量を変える・外す → 確定
  - 株ごとに `fertilized` イベント（target_type=mat、payload に `batch_id`）。1 回の確定は 1 回の insert（配列）か RPC。オンライン前提（件数が多いので outbox に積まない）
  - 株の詳細の履歴に施肥が出る
  - 完了条件:
    1. 6 株の圃場で 1 株を外し、1 株の量を変えて確定すると、5 件のイベントができ、量が株ごとに正しい。同じ `batch_id` で束ねられている
    2. 株の詳細に施肥の記録が出る

- [x] **2-5 圃場・株を対象にした被害**（要件 4.3、UC-6）
  - 圃場の詳細と株の詳細に「被害を記録」（種類・程度は 1-8 と同じ）。`events.target_type = field / mat`
  - 「喪失」は茎にだけ意味があるので、圃場・株の被害では選べない（株を失ったなら撤去 2-3 を使う、と案内）
  - 台風の後を想定し、圃場の被害記録から「この圃場の株に個別の被害も記録する」へ続けられる（株の一覧で選んで同じ内容を一括）
  - 完了条件:
    1. 圃場・株に被害を記録すると、それぞれの詳細の履歴に出る
    2. 圃場の被害から複数の株に一括で記録でき、株ごとにイベントができる

- [x] **2-6 記録の訂正**（要件 5.5、data-model 2.2）
  - 茎の履歴の観測・イベントに「訂正」。観測は新しい値を、イベントは payload の項目を入れ直す → 新しいレコードを追加し、元の `superseded_by` に新しい id を入れる（0001 のトリガーが `superseded_by` 以外の更新を拒否する）
  - 累計葉数・検算・履歴の表示は `superseded_by is null` の行だけを使い、訂正済みの行は履歴で打ち消し線＋「訂正済み」
  - 茎の状態を変えたイベント（出蕾・収穫・被害の喪失）の訂正は、日付と payload の数値だけを直せる（イベントの種類は変えられない）。状態を戻す取り消しは扱わない（必要なら別タスク）
  - 完了条件:
    1. +1 の観測を +2 に訂正すると累計葉数が 1 増え、履歴に元の行が「訂正済み」で残る
    2. 収穫の重量を訂正すると、新しい重量が表示される。元の行は残る
    3. どの行も削除できない（削除の UI がない）

- [x] **2-7 今週見る株**（画面 1）
  - ホームに「今週見る株」: 栽培中・出蕾済みの茎を持つ株を、**前回の葉数の観測からの経過日数**の長い順に並べる（既定: 7 日以上で表示。設定で 7 / 14 日）。各行に株コード、圃場、最も進んだ茎の状態と累計葉数、経過日数。タップで株の詳細
  - 出蕾済みの茎は上に出す（袋掛け・収穫の時期が近いため）。積算温度による並べ替えはステップ 3 で足す
  - 今日記録した株は消える（巡回の進み具合が分かる）
  - 並べ替えは `src/lib/` の純粋関数にして単体テスト
  - 完了条件:
    1. 8 日前に記録した株と 2 日前に記録した株があるとき、前者だけが出る
    2. その株で +1 を記録してホームに戻ると、一覧から消えている
    3. 出蕾済みの株が一覧の上に出る

- [x] **2-8 現在地から近い株**（画面 2）
  - 地図に現在地ボタン（Geolocation）。現在地を点で表示し、近い順に 3 株を下部に候補として出す（距離 m 付き）。タップで株の詳細
  - 距離計算は `src/lib/geo.ts`（既存）を使い、単体テスト
  - 位置情報を拒否されたら理由を表示（地図は普通に使える）
  - 完了条件:
    1. 位置を固定した状態（Playwright の `geolocation`）で、近い順に 3 株と距離が出る
    2. 位置情報が拒否されても地図が使え、理由が表示される

- [x] **2-9 読み取りのローカルキャッシュ**（offline-sync.md 5 章）
  - 圃場・株・茎・観測・イベント・写真のメタデータを Dexie にキャッシュし、`updated_at`（ない表は `created_at`）で差分取得。必要なら `updated_at` 列とトリガーをマイグレーションで追加
  - 画面はまず端末のデータを表示し、裏でサーバーと差分同期して更新する（開いた瞬間に出る）
  - 圏外でも、一度同期した圃場・株・茎の画面を開いて記録できる（1-9 の制限「開いておいた茎の画面だけ」をなくす）。履歴画面にも未送信分を重ねる
  - 完了条件:
    1. オンラインで一度ホームを開いた後、オフラインで別の株・別の茎の画面を開いて +1 を記録でき、オンラインに戻すと同期される
    2. 別の端末（別のブラウザコンテキスト）で記録したものが、差分同期でこちらに出る
    3. 画面の表示速度が PERF-1 の「後」より悪化していない（perf.md に追記）

2-6 の後に残したもの（訂正の対象拡大）:
- 2-6 で訂正できるのは茎の観測（`leaves_new` / `leaves_current` / `pseudostem_girth_cm` / `height_cm`）と茎のイベント（出蕾・段数・袋掛け・摘蕾・収穫・枯葉処理・被害）の日付と payload の数値だけ。吸芽系（`sucker_emerged` / `sucker_adopted` / `sucker_removed` / `sucker_transplanted`、2-1・2-2）、施肥・圃場/株の被害（2-4・2-5）、写真の訂正は扱っていない。イベントの種類の変更と状態を戻す取り消し（出蕾・収穫・喪失をなかったことにする）も扱っていない
- 訂正はオンライン前提（outbox に積まない）。未同期の記録は同期してから訂正する

ステップ 2 の前に決めておくとよい要確認（`01_requirements.md` 10 章）: 2 番（列数・本数）、11 番（撤去の扱い → 2-3 の案で確定してよいか）、15 番（吸芽の方向）。

ステップ2に含めるもの（元のメモ。上のタスクに変換済み）:

## ステップ 3: 予測と提案

目的: 出蕾を記録した茎の収穫時期を、自圃場の気温（積算温度）から予測し、袋掛け・収穫期・追肥・枯葉処理・確認を提案する。
設計は `docs/02_design/prediction.md`。順序: 3-1 → 3-2 → 3-3 は必須の順序（気温がないと積算温度が出ず、積算温度がないと予測が出ない）。3-4 は 3-3 の後、3-5・3-6 は 3-4 の後。
暫定の初期値は `01_requirements.md` 10 章の「ステップ 3 の暫定値」。すべて設定で変えられるようにし、実績で補正する。

- [x] **3-1 気温の取り込み**（prediction.md 1 章、architecture.md 5 章）
  - Open-Meteo から圃場の代表点（`weather_lat/lng` があればそれ）の時間別気温・降水・最大風速を取り込み、`weather_hourly` と `weather_daily`（日平均・最低・最高・降水）に保存。`temperature_offset_c` を加える
  - 取り込みは 1 日 1 回（Vercel Cron → Route Handler。認証はシークレットのヘッダ）。初回と取りこぼしは、圃場の登録日（または最も古い茎の `started_at`）まで遡って過去 API で埋める
  - 平年値の材料として、過去 10 年分の日別気温も同じ表に取り込む（`source` を分けるか、別表。3-2 で使う）
  - 失敗（API の障害）は次回に取りこぼし分をまとめて取る。取り込みの記録（最終取得日時・件数・エラー）を残し、圃場の詳細に「気温: 最終取得 日時」を出す
  - 完了条件:
    1. 圃場を登録すると、登録日までの日別気温が `weather_daily` に入る（E2E では Open-Meteo をモックしてよい）
    2. 日次の取り込みを 2 回走らせても行が重複しない
    3. API が失敗しても次回の取り込みで欠けた日が埋まる

- [ ] **3-2 積算温度と平年値**（prediction.md 1 章）
  - `src/lib/gdd.ts`: 日次 GDD（時間別があれば時間平均、なければ日平均。基準温度は品種、圃場×品種で上書き）、期間の積算、平年値（過去 10 年の同じ日の平均。2/29 の扱いを決める）。単体テスト
  - 茎の画面（出蕾済み）に「出蕾から N 日、積算温度 X ℃・日」を出す。株・茎の画面に表示するのは実績のみ（予測は 3-3）
  - 完了条件:
    1. 既知の気温の並びで、日次 GDD・期間の積算・平年値が手計算と一致する（単体テスト）
    2. 出蕾済みの茎の画面に、出蕾からの日数と積算温度が出る
    3. 基準温度を圃場×品種で変えると積算温度が変わる

- [ ] **3-3 収穫予測日**（prediction.md 2・7 章）
  - 出蕾済みの茎について、出蕾日からの実績 GDD ＋ 明日以降の平年値で「目標 GDD に達する日」を予測日とし、目標の ±10% で幅を出す。`estimates` に追記（`model_version`、`inputs` に出蕾日・目標 GDD・実績 GDD・平年値の版）。出蕾の記録時と、日次の気温取り込みの後に再計算
  - 目標 GDD は品種の既定（暫定値）、圃場×品種で上書き。設定画面（圃場の詳細）で変えられる
  - 被害: 茎の被害が severe なら推定に「要確認」。lost の茎は推定しない。圃場・株の severe の被害（2-5）は、その圃場・株の茎を「要確認」にする（prediction.md 7 章の未決をこの案で確定）
  - 出蕾日は確認日を使う（`earliest_at` は inputs に残すだけ）。出蕾時の累計葉数は予測に使わない（スナップショットの扱いは関係しない）
  - 茎の画面に「収穫予測: ◯月◯日ごろ（◯日〜◯日）」、株の詳細の茎一覧にも予測日
  - 完了条件:
    1. 出蕾を記録すると、茎の画面に予測日と幅が出る。`estimates` に model_version と inputs 付きで追記される（上書きしない）
    2. 目標 GDD を変えると、再計算で予測日が変わり、古い推定も残っている
    3. severe の被害がある茎は「要確認」、lost の茎は予測が出ない

- [ ] **3-4 提案の基盤と、袋掛け・摘蕾・収穫期**（prediction.md 6 章）
  - `src/lib/recommendations/`: ルールを純粋関数で（入力: 茎・イベント・推定・設定・今日、出力: 作るべき提案）。同じ対象・同じ kind で open があれば作らない。対象の茎が終了（lost / harvested / removed / transplanted）したら open を dismissed（理由「対象が終了」）
  - ルール: 袋掛け・摘蕾（出蕾から N 日、袋掛け・摘蕾が未記録）、収穫期（予測の下限が 7 日以内）
  - 実行: イベント記録の後と日次バッチ（3-1 の Cron の後）
  - ホームの「提案」区画（今週見る株の上）: 期限順、各行に対象（株コード・茎）、理由、期限、「実施した」「無視」。「実施した」は記録画面へ導く（袋掛けなら茎の画面の袋掛け）。対応するイベントが記録されたら自動で done
  - N は設定（圃場ごと）
  - 完了条件:
    1. 出蕾から N 日たった茎に「袋掛け・摘蕾」の提案が出て、袋掛けを記録すると done になる
    2. 予測の下限が 7 日以内の茎に「収穫期」の提案が出る。収穫を記録すると done、喪失すると dismissed
    3. 同じ提案が二重にできない。「無視」は dismissed として残り、再び作られない

- [ ] **3-5 収穫後の追肥・枯葉処理・確認の提案**（prediction.md 6 章）
  - 収穫後の追肥: 収穫を記録した株に、M 日以内に施肥（2-4）がなければ提案。量は圃場の標準量（設定。未設定なら量を出さず「圃場の標準量を設定してください」）
  - 枯葉処理: 栽培中・出蕾済みの茎で、最後の枯葉処理（または採用・植え付け）から X 日以上
  - 確認: 累計葉数の検算ずれ ≥ 3（1-6）、茎の被害が severe
  - M・X・標準量は設定（圃場ごと）
  - 完了条件:
    1. 収穫を記録すると「収穫後の追肥」が出て、その株に施肥を記録すると done になる
    2. 枯葉処理から X 日たった茎に提案が出て、枯葉処理を記録すると done になる
    3. 検算ずれ・severe の被害で「確認」が出る

- [ ] **3-6 予測一覧（画面 7）**
  - `/forecast`（UX-1 のプレースホルダーを置き換え）: 週ごと（月曜始まり）の収穫予定本数（重量は ステップ 4）、要確認は別枠。茎ごとの一覧（株コード・圃場・出蕾日・予測日と幅・要確認）。圃場で絞り込み。PC でも iPhone でも読める
  - 完了条件:
    1. 出蕾済みの茎が予測日の週に数えられる。lost は数えず、要確認は別枠
    2. 圃場で絞り込める
